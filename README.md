# مقدمة المشروع

مشروع **محاكي اختبار CEH التدريبي** هو منصة تدريبية مخصصة لمحاكاة بيئة اختبار شهادة **Certified Ethical Hacker** بصورة عملية ومنظمة. الهدف من هذه المنصة ليس فقط عرض الأسئلة وحساب الدرجة، بل بناء تجربة اختبار قريبة قدر الإمكان من جلسة حقيقية تتطلب التزامًا ومراقبة وتركيزًا طوال مدة الحل.

تم تصميم المشروع ليدعم سيناريو تدريبي واضح: المدرب يقوم بإدخال الأسئلة يدويًا في بنك الأسئلة، ثم تبدأ المتدربة جلسة اختبار جديدة باسمها، وتُسحب الأسئلة من قاعدة البيانات وتُعرض داخل واجهة عربية رسمية. أثناء الجلسة، يتم تفعيل الكاميرا بشكل إجباري، كما تُرصد مجموعة من السلوكيات المهمة مثل فقدان الكاميرا، ومحاولات النسخ، ومحاولات ترجمة الصفحة، إضافة إلى تقدير بصري مبسط لاتجاه النظر لاكتشاف الانحرافات المتكررة عن الشاشة.

هذا المشروع بُني باستخدام **HTML وCSS وJavaScript** في الواجهة الأمامية فقط، و**Node.js** في جهة الخادم، و**MySQL** في قاعدة البيانات، دون استخدام أطر عمل من نوع Express أو React أو Vue، ودون الاعتماد على مكتبات واجهة خارجية. هذا القرار يجعل المشروع مناسبًا للتعلم من الصفر، لأن كل جزء فيه واضح ومباشر ويمكن تتبعه بسهولة من قبل المبتدئات.

كما يركّز المشروع على الجانب التحليلي بعد انتهاء الجلسة، حيث تُعرض صفحة نتائج تجمع بين الدرجة الأكاديمية ومؤشرات السلوك أثناء الاختبار. بهذه الطريقة لا تحصل المدربة فقط على معرفة من أجابت بشكل صحيح، بل أيضًا كيف تصرفت المتدربة أثناء الجلسة، وهل وقعت محاولات مخالفة أو مؤشرات تستحق المراجعة لاحقًا.

# أهداف المشروع

يحقق المشروع مجموعة أهداف تعليمية ووظيفية مهمة:

1. توفير بيئة تدريب واقعية لمحاكاة اختبار CEH.
2. تمكين المدرب من بناء بنك أسئلة يدويًا من داخل لوحة التحكم.
3. حفظ بيانات المتدربات والجلسات والنتائج داخل قاعدة بيانات دائمة.
4. فرض تفعيل الكاميرا أثناء جلسة الاختبار وعدم السماح بالاستمرار بدونها.
5. رصد محاولات النسخ وتسجيلها زمنيًا داخل قاعدة البيانات.
6. تطبيق طبقات متعددة للحد من ترجمة الصفحة ورصد محاولات تفعيلها.
7. تنفيذ تقدير بصري مبسط لحركة الوجه واتجاه النظر عبر JavaScript فقط.
8. احتساب الوقت وإرسال الاختبار تلقائيًا عند انتهاء المدة المحددة.
9. إنتاج تقرير نهائي واضح يُسهل على المدرب مراجعة الأداء والسلوك معًا.

# الفكرة العامة وآلية العمل

تبدأ دورة العمل من **لوحة المدرب**، حيث يمكن للمدرب إدخال السؤال يدويًا مع رقم السؤال والتصنيف وأربعة خيارات وتحديد الإجابة الصحيحة. بعد حفظ السؤال، ينتقل مباشرة إلى قاعدة بيانات MySQL ليصبح متاحًا ضمن بنك الأسئلة.

عندما تدخل المتدربة إلى الصفحة الرئيسية، تكتب اسمها ثم تبدأ جلسة جديدة. الخادم ينشئ سجلًا جديدًا في جدول الجلسات ويربطه باسم المتدربة ويحدد وقت البدء وعدد الأسئلة والمدة الأساسية للجلسة. بعدها تنتقل المتدربة إلى صفحة الاختبار.

داخل صفحة الاختبار تعمل عدة طبقات في الخلفية في نفس الوقت. أولًا، تُطلب الكاميرا عبر `getUserMedia`. ثانيًا، يبدأ عداد الوقت التنازلي. ثالثًا، يُمنع النسخ والتحديد والزر الأيمن. رابعًا، يبدأ مراقب الترجمة في متابعة تغييرات الصفحة. خامسًا، يبدأ محلل بصري مبسط يلتقط إطارات من الفيديو ويقدّر ما إذا كان مركز الوجه الظاهر انحرف عن المنطقة المقبولة لفترة تتجاوز الحد المسموح.

عند التسليم اليدوي أو التلقائي، تُرسل جميع الإجابات إلى الخادم، فيُحسب عدد الإجابات الصحيحة والخاطئة والدرجة النهائية، ثم تُجمع أعداد أحداث المراقبة المسجلة سابقًا، وبعد ذلك تُعرض صفحة نتائج تفصيلية، وتبقى جميع البيانات محفوظة في قاعدة البيانات بحيث يستطيع المدرب العودة إليها لاحقًا من لوحة الجلسات.

# التقنيات المستخدمة ولماذا استُخدمت

## HTML

استُخدمت HTML لبناء الصفحات الأساسية للمشروع، وهي:

1. الصفحة الرئيسية لبدء الجلسة.
2. صفحة الاختبار.
3. صفحة النتائج.
4. لوحة المدرب.

تم اختيار HTML لأنها البنية الأساسية لأي واجهة ويب، وهي كافية تمامًا لبناء صفحات ثابتة ومنظمة دون الحاجة إلى أي إطار عمل.

## CSS

استُخدمت CSS لتصميم الواجهة الرسمية العربية، مع خطوط واضحة وأزرار دائرية الحواف ومسافات مدروسة وحدود كاملة للعناصر بدلًا من أشكال البطاقات ذات الخط الجانبي الممنوع. كما استُخدمت CSS أيضًا في طبقة مقاومة الترجمة لإخفاء بعض العناصر التي قد يحقنها المتصفح عند تشغيل الترجمة.

## JavaScript

استُخدمت JavaScript في الواجهة الأمامية لأنها مسؤولة عن السلوك التفاعلي كله تقريبًا، مثل:

1. جلب الأسئلة من الخادم.
2. بدء جلسة الاختبار.
3. إدارة الانتقال بين الأسئلة.
4. تشغيل الكاميرا.
5. تتبع الوقت.
6. منع النسخ.
7. مراقبة الترجمة.
8. تحليل الإطارات المرئية تقديريًا لرصد انحراف النظر.

## Node.js

استُخدم Node.js لبناء الخادم الخلفي لأن المطلوب ينص صراحة على استخدامه. الخادم هنا يعمل عبر الوحدات المدمجة مثل `http` و`fs` و`url` بدلًا من الاعتماد على إطار عمل خارجي. هذا الأسلوب يجعل المشروع قريبًا من الأساسيات ويكشف بوضوح كيف تُبنى المسارات البرمجية وطلبات HTTP يدويًا.

## MySQL

استُخدمت MySQL لأنها قاعدة بيانات علائقية قوية ومناسبة لحفظ:

1. بيانات المتدربات.
2. الأسئلة.
3. الخيارات.
4. الجلسات.
5. الإجابات.
6. أحداث المراقبة.

وجود علاقات واضحة بين هذه الجداول يجعل تتبع كل جلسة وكل حدث مرتبط بها أمرًا منظمًا جدًا.

## mysql2

استُخدمت حزمة `mysql2` فقط كوسيط اتصال بين Node.js وMySQL. هذه ليست إطار عمل، بل طبقة اتصال لازمة عمليًا لتنفيذ أوامر SQL من داخل الخادم. دونها لن يستطيع الخادم فتح اتصالات قاعدة البيانات بشكل مباشر من Node.js.

# قاعدة البيانات وتصميم الجداول

قاعدة البيانات اسمها:

`ceh_mock_exam`

تم تقسيمها إلى جداول مترابطة حتى تعكس الواقع الفعلي للمشروع.

## جدول المتدربات `trainees`

هذا الجدول يحفظ كل متدربة بالاسم. عند بدء جلسة جديدة، إذا كان الاسم موجودًا سابقًا يُعاد استخدام نفس السجل، وإذا لم يكن موجودًا يُنشأ سجل جديد.

أهم الأعمدة:

1. `id` المعرف الأساسي.
2. `name` اسم المتدربة.
3. `created_at` وقت إضافة المتدربة لأول مرة.

## جدول الأسئلة `questions`

يحفظ النص الأساسي للسؤال ومعلوماته العامة.

أهم الأعمدة:

1. `question_number` رقم السؤال إن أراد المدرب استخدام ترقيمه المرجعي.
2. `category` تصنيف السؤال.
3. `question_text` نص السؤال.
4. `correct_option_key` حرف الخيار الصحيح مثل `A` أو `B`.

## جدول الخيارات `question_options`

فصل الخيارات في جدول مستقل أفضل من تخزينها كلها في عمود واحد، لأن هذا يجعل البنية أوضح وأسهل للاستعلام والتعديل.

أهم الأعمدة:

1. `question_id` معرّف السؤال المرتبط.
2. `option_key` رمز الخيار مثل `A`.
3. `option_text` نص الخيار.

## جدول الجلسات `exam_sessions`

هذا من أهم الجداول لأنه يمثل سجل الجلسة الكامل من البداية للنهاية.

أهم الأعمدة:

1. `trainee_id` يربط الجلسة بالمتدربة.
2. `started_at` وقت بداية الجلسة.
3. `ended_at` وقت النهاية.
4. `duration_seconds` المدة المستغرقة فعليًا.
5. `total_questions` عدد أسئلة الجلسة.
6. `correct_count` عدد الإجابات الصحيحة.
7. `wrong_count` عدد الإجابات الخاطئة.
8. `score_percent` الدرجة النهائية بالنسبة المئوية.
9. `eye_suspicious_count` عدد أحداث حركة العين المشبوهة.
10. `copy_attempts_count` عدد محاولات النسخ.
11. `camera_loss_count` عدد مرات فقدان الكاميرا.
12. `translate_attempts_count` عدد محاولات الترجمة.
13. `status` حالة الجلسة مثل مكتملة أو تسليم تلقائي.

## جدول إجابات الجلسة `session_answers`

يحفظ إجابة المتدربة على كل سؤال داخل الجلسة. هذا يفيد لاحقًا لو أردتِ عرض تحليل أعمق لكل سؤال.

## جدول أحداث المراقبة `monitoring_events`

هذا الجدول يسجل كل مخالفة أو حدث رقابي مع وقته الدقيق ونوعه والتفاصيل النصية المرتبطة به.

أنواع الأحداث الحالية:

1. `eye_suspicious`
2. `copy_attempt`
3. `camera_loss`
4. `translate_attempt`

## العلاقات بين الجداول

1. كل متدربة يمكن أن تمتلك عدة جلسات.
2. كل جلسة تنتمي إلى متدربة واحدة.
3. كل سؤال يمتلك عدة خيارات.
4. كل جلسة يمكن أن تحتوي على عدة إجابات.
5. كل جلسة يمكن أن تحتوي على عدة أحداث مراقبة.

# تدفق العمل من البداية حتى التقرير النهائي

يمكن تلخيص تدفق النظام على النحو التالي:

1. المدرب يدخل أسئلة جديدة من لوحة المدرب.
2. الخادم يحفظ السؤال والخيارات في MySQL.
3. المتدربة تدخل اسمها من الصفحة الرئيسية.
4. الخادم ينشئ جلسة جديدة في جدول `exam_sessions`.
5. صفحة الاختبار تجلب الأسئلة من الخادم.
6. الكاميرا تُفعّل إجباريًا.
7. يبدأ المؤقت وتبدأ طبقات المراقبة.
8. عند كل مخالفة يتم إرسال حدث إلى API وتخزينه في `monitoring_events`.
9. عند التسليم تُرسل الإجابات للخادم.
10. الخادم يحسب النتيجة ويحدّث سجل الجلسة.
11. صفحة النتائج تعرض التقرير النهائي.
12. المدرب يمكنه الرجوع لكل الجلسات السابقة من لوحة المدرب.

# شرح الخوارزميات والآليات الرقابية

## أولًا: تفعيل الكاميرا الإجباري

تعتمد هذه الآلية على الدالة `getUserMedia` الموجودة في المتصفح. هذه الدالة تطلب إذن الوصول إلى كاميرا الجهاز. إذا سمحت المتدربة، يبدأ بث الفيديو داخل عنصر `video`. إذا رفضت، أو إذا توقف مسار الفيديو بعد أن بدأ، يعتبر النظام أن الكاميرا فقدت.

عند فقدان الكاميرا:

1. يتوقف الاختبار مؤقتًا.
2. تظهر نافذة واضحة تطلب إعادة التفعيل.
3. يُسجَّل حدث `camera_loss`.
4. لا تعود الجلسة حتى تنجح إعادة تشغيل الكاميرا.

## ثانيًا: رصد حركة العين المشبوهة

من المهم توضيح نقطة أساسية: المشروع هنا لا يستخدم مكتبات ذكاء اصطناعي أو نماذج جاهزة لتتبع العين بدقة احترافية، لأن المطلوب يمنع ذلك. لذلك استُخدمت خوارزمية **تقدير بصري مبسط** تعتمد على قراءة إطارات الفيديو من الكاميرا وتحليل توزع ألوان الوجه داخل الصورة.

### شرح مبسط للمصطلحات

**الإطار المرئي** هو صورة واحدة ملتقطة من الفيديو.

**Canvas** هو سطح رسم داخل المتصفح يمكن من خلاله أخذ لقطة من الفيديو وتحويلها إلى بيانات بكسلات.

**البكسل** هو أصغر نقطة لونية في الصورة.

### كيف تعمل الخوارزمية

1. تؤخذ لقطة صغيرة من الفيديو بشكل متكرر.
2. تُفحص البكسلات لاستخراج مجموعة بكسلات يُحتمل أنها تمثل الجلد بناء على قيم اللون `RGB`.
3. يُحسب مركز هذه المجموعة داخل الإطار.
4. يُقاس بُعد هذا المركز عن المنطقة المتوقعة لوجود الوجه في منتصف الصورة.
5. إذا تجاوز البعد حدًا معينًا، يعتبر النظام أن هناك انحرافًا.
6. إذا استمر الانحراف أكثر من الحد الزمني المحدد، يُسجل الحدث كحركة عين أو وجه مشبوهة.

### لماذا هذا الحل مقبول هنا

لأنه يحقق المطلوب ضمن القيود المسموحة، ويقدم طبقة مراقبة عملية، لكنه ليس بديلًا عن أنظمة الرؤية الحاسوبية المتقدمة. لذلك يجب فهمه على أنه **رصد تقريبي تدريبي** وليس حكمًا نهائيًا عالي الدقة.

## ثالثًا: منع النسخ

تم تطبيق منع النسخ على عدة مستويات:

1. اعتراض حدث `copy`.
2. اعتراض حدث `cut`.
3. اعتراض اختصارات لوحة المفاتيح مثل `Ctrl + C`.
4. تعطيل `selectstart` لمنع تحديد النص.
5. تعطيل `contextmenu` لمنع الزر الأيمن.
6. تعطيل السحب `dragstart`.

كل محاولة تُسجل في قاعدة البيانات كحدث `copy_attempt` مع تفاصيل مختصرة عن مصدر المحاولة.

## رابعًا: منع الترجمة بطبقات متعددة

بسبب طبيعة المتصفحات الحديثة لا يمكن لأي موقع أن يمنع الترجمة بنسبة 100% في كل الحالات، لكن يمكنه بناء طبقات ردع واكتشاف قوية. المشروع يطبق هذه الطبقات كالتالي:

1. وضع الوسم:
   `meta name="google" content="notranslate"`
2. وضع `translate="no"` على `html` و`body` وباقي العناصر.
3. كتابة CSS يستهدف العناصر الشائعة التي تحقنها خدمات الترجمة داخل الصفحة.
4. تشغيل `MutationObserver` لمراقبة تغييرات DOM واكتشاف العناصر أو الفئات المشبوهة.
5. مراقبة خاصية `lang` وإعادتها إلى `ar` إذا تغيرت.
6. عند اكتشاف محاولة ترجمة تُرسل مخالفة `translate_attempt` للخادم ويظهر تنبيه مباشر.

## خامسًا: حساب الوقت والتسليم التلقائي

عند بدء الاختبار يُضبط عدد الثواني المتبقية حسب القيمة الموجودة في `config.js`. بعد ذلك يعمل مؤقت عبر `setInterval` ينقص ثانية واحدة في كل دورة. عندما يصل العداد إلى الصفر، ينفّذ النظام وظيفة التسليم التلقائي ويرسل الإجابات الحالية إلى الخادم مع وسم أن التسليم كان تلقائيًا.

# مقتطفات كود مهمة مع الشرح

## إنشاء جلسة اختبار جديدة

```js
const result = await db.query(
    'INSERT INTO exam_sessions (trainee_id, started_at, total_questions, status) VALUES (?, ?, ?, ?)',
    [traineeId, formatDateTime(now), total, 'active']
);
```

هذا المقتطف ينشئ سجلًا جديدًا للجلسة فور بدء الاختبار. استخدام علامات الاستفهام `?` هنا مهم جدًا لأنه يسمى **الاستعلام المعلَّم** أو **Parameterized Query**، وهو الأسلوب الصحيح لحماية الاستعلام من الإدخال الضار.

## تسجيل حدث مراقبة

```js
await db.query(
    'INSERT INTO monitoring_events (session_id, event_type, occurred_at, details) VALUES (?, ?, ?, ?)',
    [sessionId, eventType, now, details || null]
);
```

كل مخالفة أو ملاحظة رقابية تمر من هذا السطر تقريبًا. هذا يجعل المشروع منظمًا لأن كل الأحداث، مهما اختلف نوعها، تتجمع في جدول واحد موحد.

## طلب تفعيل الكاميرا

```js
this.stream = await navigator.mediaDevices.getUserMedia({
    video: { facingMode: 'user', width: { ideal: 640 }, height: { ideal: 480 } },
    audio: false
});
```

هنا تطلب الواجهة الأمامية الوصول إلى كاميرا المتدربة الأمامية. تم تعطيل الصوت لأن المطلوب الحالي يركز على المراقبة البصرية فقط.

## مراقبة DOM لاكتشاف الترجمة

```js
this.observer = new MutationObserver((mutations) => {
    mutations.forEach((mutation) => {
        if (mutation.type === 'childList') {
            mutation.addedNodes.forEach((node) => {
                if (node.nodeType === 1 && this.isTranslateElement(node)) {
                    this.handleTranslateDetection('عنصر ترجمة جديد');
                }
            });
        }
    });
});
```

هذا المقتطف يراقب التغييرات داخل الصفحة. إذا أضاف المتصفح عنصرًا يُشبه عناصر الترجمة المعروفة، يُسجل النظام محاولة مخالفة ويُظهر تنبيهًا.

## تحليل الإطار البصري

```js
const centerX = sumX / count;
const centerY = sumY / count;
const normX = Math.abs(centerX / w - 0.5);
const normY = Math.abs(centerY / h - 0.4);
const deviation = Math.sqrt(normX * normX + normY * normY);
```

هذا الجزء يحسب مركز كتلة البكسلات التي يُرجح أنها تمثل الوجه، ثم يقيس مسافة هذا المركز عن المنطقة المتوقعة داخل الإطار. إذا زادت المسافة عن الحد المحدد ولفترة كافية، يُعتبر ذلك انحرافًا مشبوهًا.

# المشاكل المعروفة وحدود الحل

## 1) تتبع العين هنا تقديري وليس احترافيًا بالكامل

بسبب منع استخدام المكتبات الخارجية أو نماذج الرؤية الحاسوبية الجاهزة، فإن رصد حركة العين يعتمد على تحليل بصري مبسط للوجه داخل الإطار. هذا يحقق المطلوب تدريبيًا، لكنه قد يتأثر بالإضاءة، ولون الخلفية، وجودة الكاميرا، وزاوية الجلوس.

## 2) منع الترجمة لا يمكن ضمانه بنسبة 100%

الموقع يطبق أقصى ما يمكن عبر الوسوم والأنماط ومراقبة DOM وإرجاع `lang`، لكن المتصفح في النهاية يظل تحت تحكم المستخدم. لذلك قد تُمنع معظم الحالات أو تُرصد، لكن لا يمكن تقديم تعهد مطلق بإيقافها دائمًا في كل إصدار من كل متصفح.

## 3) المشروع لا يحتوي نظام تسجيل دخول

هذا تم عن قصد لأن الطلب ركز على التدريب وإدارة الأسئلة والجلسات، ولم يطلب طبقة مصادقة أو صلاحيات متعددة.

## 4) البيانات الأولية محدودة

ملف `schema.sql` يضيف عددًا صغيرًا من الأسئلة التجريبية فقط لتسهيل التشغيل الأول. الاستخدام الحقيقي يحتاج أن يبني المدرب بنك الأسئلة الكامل يدويًا.
